# 反馈闭环：一句话反馈怎么变成下个版本

> 这篇不是流程文档，是**入口**。用户说一句「这里不对」，必须有唯一的落点，
> 否则同一类问题会在第 6 篇文章里原样复发。

---

## 1. 触发

三种情况都算一次反馈：

- 用户指出错误（「这句译反了」「这页太丑」「等太久」）；
- 脚本报红（gate / check-content / smoke 任一失败）；
- 独立审校在**两篇不同文章**里报出同类问题。

## 2. 归类：只允许三个落点

| 判断 | 落点 | 具体做什么 |
|---|---|---|
| 能写成程序判断 | **工具** | 改 `tools/*.mjs`，加一条断言；`gate.mjs` 里能看见 |
| 不能程序判，但能举反例 | **样例** | 写进 `references/07-cases.md`（好例子 / 坏例子 + 为什么） |
| 依赖判断、取舍、审美 | **文档** | 改 `SKILL.md` / `references/*`，或 `05-pitfalls.md` 新增一条 |

**优先顺序就是上表顺序。** 能进工具的别写进提示词——提示词每加一句，都是每个会话的固定成本，
而且靠自觉执行；断言不靠自觉。

## 3. 单次要求 vs 长期规则

- **单次要求**（这篇要这样）→ 记在该项目的 `SPEC.md` 或 `QA.md` 的「本次特例」，**不进 skill**。
- **同类第二次出现** → 升级为长期规则（工具 > 样例 > 文档）。
- 判据不是「我觉得重要」，而是**有两条独立记录**。台账见 §5。

反例：用户某篇说「标题再小一点」，不要改 `style.css` 的全局字号；
连着三篇都这么说，才改模板。

## 4. 一次反馈的完整循环（5 步）

1. **复现**：哪种输入下会出错？先 `cp -R` 成品到 `/tmp/bil-fixtures/` 做个副本，能复现再动手。
2. **落点**：按 §2 选一个，不要三个都改。
3. **改 + 验证**：工具类必须有一条能跑的命令证明「改前红、改后绿」；
   文档类要检查与现有条目冲突（`grep` 关键词，别制造两套说法）。
4. **回归**：把 5 篇成品复制到 `/tmp/bil-fixtures/` 后跑 `gate.mjs`（成品目录只读，别在里面构建），确认没有把原来绿的跑红。
5. **记账**：`CHANGELOG.md` 加一行（版本号 + 日期 + 为什么）；`06-feedback.md` §5 加一行台账；
   如果新增了坑，`05-pitfalls.md` 那条要写清「由谁兜住」。

## 6. 什么时候**不**改 skill

- 只有一篇文章碰到的问题（写成 `SPEC.md` 的特例）；
- 属于「这篇要不要加白话版」这类**每篇四问**的选择（走 `ask_user_question`，不进 skill）；
- 工具修不了、样例也说不清、只能靠审校的语义问题——那就只补审校提示词里的一条检查项，
  并为它配一条真实反例（没有反例的检查项会被审校忽略）。

## 7. 版本

- 版本号写在 `SKILL.md` 顶部与 `data/skill.json`（scaffold 自动写）。
- 每次改动追加到 skill 根目录的 `CHANGELOG.md`（Keep a Changelog 格式）。
- 旧项目升级：`node scaffold.mjs --refresh <项目>`（只换 tools/；`--src` 才碰页面模板）。
